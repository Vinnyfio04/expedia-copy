# Assignment instructions

Updated October 1, 2026. We had not previously covered how to make a change end to end, from the database through the backend to the frontend. We consider this an important workflow for students to learn. To give everyone a common starting point, we created the October 1 tutorial, [[In-class Activity] Local Hotel Storage and Manual Verification](https://psu.instructure.com/courses/2484533/pages/in-class-activity-local-hotel-storage-and-manual-verification), with demonstrations and validated prompts. Its [graded companion activity](https://psu.instructure.com/courses/2484533/assignments/18765499) identifies the local-storage checkpoint.

Assignment 2 Part 2 now extends that working foundation by adding business intelligence to the Part 1 application through a RAG-based LLM chatbot. Saving data locally is the starting point for Part 2; full credit now requires the retrieval and answer-generation workflow below. The in-class activity and its graded companion retain their own mandatory stopping point.

Model choice: Use one of the following: a paid OpenAI API, the Gemini API, or the free Nemotron option demonstrated in class through [OpenRouter](https://openrouter.ai/models?fmt=free). Use the class configuration for Nemotron and check the selected model's current availability and usage limits. You only need to integrate one provider.

1. Start with saved data. Continue from the tutorial's local SQLite implementation: saved API hotels, ZIP/location context, and dated demo nightly rates and room availability. Preserve Add to Local, Remove from Local, persistence, and local-first lookup. Preserve the frozen Part 1 API, ZIP search, and list/map behavior, along with the Assignment 1 tables and supplied records. Clearly label the demo rates and availability as simulated course data.
2. Accept a natural-language question. Add a chatbot interface where the user can express a hotel-search or comparison intent. Show loading, answer, and failure states.
3. Generate and execute a focused query. The backend sends the question, relevant database schema, and query rules to the chosen LLM. The model creates or adjusts an SQL query to match the user's intent. The backend validates the proposal and executes only an allowed, read-only query over the relevant local hotel and demo-night tables, with bounded results. The remote model does not directly access SQLite.
4. Augment the answer with retrieved records. Send the original question and the limited, relevant database results to the LLM in a second request. Ask it to produce an answer grounded in those records, rather than guessing missing prices, vacancies, or hotels.
5. Present an actionable result. Display the answer in the frontend so the user can understand the matching hotels, relevant dates, costs, availability, and reason for the recommendation. Clearly report no matches or insufficient data. For a multi-night comparison, use the requested stay's nightly records and total cost; checkout is excluded and missing nights must not be treated as available.

This activity uses SQL-based retrieval from SQLite. A vector database is not required. Keep model requests and credentials on the backend. The chatbot retrieves and explains information; it does not change database records or make bookings.

Full-credit endpoint: Demonstrate the complete question → proposed SQL → checked backend retrieval → second LLM request using retrieved records → grounded frontend answer workflow, on top of the working local-storage foundation. In the report and demo, show the question, proposed query, retrieved records, and resulting answer, with expected-versus-observed checks. Include a successful question, a no-match or insufficient-data case, and evidence that an invalid or disallowed query cannot modify the database. Use labeled fixtures or mocks for failure checks and distinguish them from successful live model calls.

Before adding a dependency, the agent must CHECK the existing environment, TAKE ACTION only after explaining the exact proposed installation and receiving the student’s approval, and VERIFY the result. Existing working behavior should be preserved.
